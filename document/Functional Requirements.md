# 기능 정의

<aside>
💡

아래 기능정의는 필수적으로 들어가야하는 기능을 최소한으로 정의한 것이다.

이를 토대로 사용자 시나리오를 작성하고 (UI flow), 시나리오를 토대로 상세 요구사항을 정의한다 (functional requirements).

요구사항을 정의할 때는 edge case에 대해서도 함께 기술한다.

</aside>

## 🎬 영화

영화 검색은 제목, 감독명, 배우명으로 조회할 수 있으며, 개봉일, 인기순, 장르, 상영 유형, 날짜로 필터링이 가능해야 한다. 일반 유저와 어드민은 각기 다른 인터페이스로 해당 기능을 이용해야 한다.

어드민은 영화의 생성, 수정, 삭제를 할 수 있는 영화 관리 페이지에 접근할 수 있어야 한다.

영화, 감독, 배우 각각에 대한 상세 페이지가 제공되며, 영화 상세페이지에서는 ‘예매하기’ 버튼을 통해 해당 영화가 선택된 예매 페이지로 이동해야 한다.

---

## 🏢 상영관

어드민은 상영관을 생성, 수정, 삭제할 수 있는 상영관 관리 페이지에 접근할 수 있어야 한다.

각 상영관은 좌석 정보를 포함하며, 어드민은 좌석의 생성, 수정, 삭제 기능을 통해 좌석 배치를 관리할 수 있어야 한다.

상영관 상세 페이지에서는 좌석 정보와 함께 상영 일정을 확인할 수 있어야 한다.

---

## 🗓️ 상영 일정

어드민은 상영 일정을 생성, 수정, 삭제할 수 있어야 하며, 이 기능은 상영 일정 관리 페이지에서 제공된다.

예매 페이지에서는 상영 일정이 존재하는 모든 영화 리스트와 날짜를 제공해야 하며, 날짜를 선택하면 해당 날짜의 상영관 및 영화별 상영 일정을 확인할 수 있어야 한다. 어드민은 이 페이지에서 상영 일정에 대한 수정/삭제/추가 버튼을 볼 수 있어야 한다.

상영 일정 상세 페이지에서는 선택된 상영 일정에 대한 영화 정보, 시간, 상영관, 잔여 좌석 등의 정보를 확인할 수 있어야 한다.

---

## 🎟️ 예매

예매는 고객 유형별 인원 수를 선택한 후, 인원 수에 맞게 예매 좌석을 선택하고 결제까지 완료되면 완료된다.

예매 취소는 사용자가 환불 요청을 통해 진행할 수 있으며, 결제 완료 여부 및 상영 시간 이전 여부에 따라 처리된다.

사용자는 예매 확인 기능을 통해 자신이 예매한 영화 및 좌석 정보를 확인할 수 있어야 한다.

상영이 아직 시작되지 않은 예매 목록은 별도로 분리하여 확인할 수 있어야 하며, 마이페이지에서는 전체 예매 리스트가 조회 가능해야 한다.

---

## 💳 결제

결제는 포인트 사용 여부 선택, 결제 수단 선택, 제휴사 선택을 기반으로 총 할인가를 계산한 후 결제 API를 호출하여 진행된다. 결제가 완료되면 포인트가 적립된다.

환불은 예매된 항목에 대해 환불 요청을 통해 진행되며, 결제 내역과 연결되어 환불 처리가 이루어진다.

---

## 👤 고객

사용자는 회원가입을 통해 계정을 생성할 수 있으며, 이후 로그인하여 서비스에 접근할 수 있다.

로그인은 회원용과 어드민용으로 구분되며, 비회원도 제한된 기능에 대해 로그인 없이 접근 가능하다.

사용자는 로그아웃 기능을 통해 세션을 종료할 수 있어야 하며, 마이페이지에서 포인트를 확인하고 회원 정보를 수정할 수 있어야 한다.

회원 탈퇴 기능을 통해 계정을 삭제할 수 있으며, 이때 관련 예매 및 포인트 정보도 함께 처리되어야 한다.

---

## 🛠 어드민

어드민 계정은 별도로 생성되며, 기존 어드민에 의해 추가/삭제될 수 있어야 한다.

# 상세 기능 정의 (API 기준 + 안에서 수행하는 기능)

- 삭제 정책, 검색 조건

### 영화 생성하기

- 관리자 권한이 존재해야 한다.
- 입력
    - 영화제목, 시놉시스, 상영 시간, 영화 등급, 포스터, 개봉일, 배급사명, 감독 ID를 입력으로 받는다.
    - 상영 유형 리스트를 입력으로 받는다.
    - 배우 ID와 역할, 캐스팅 타입 리스트를 입력으로 받는다.
    - 장르명 리스트를 입력으로 받는다.
- 검증
    - 이미 존재하는 영화 제목이 있는지 확인한다.
    - 0 < 상영시간(분) < 1000
        - 위 2가지에 대해 실패 시 `Bad Request` 예외를 발생시킨다.
- 다음을 하나의 트랜잭션으로 수행한다.
    - 포스터를 스토리지에 저장시킨다.
    - 영화 테이블에 영화를 생성한다.
    - 상영 유형 테이블에 상영 유형 정보를 생성한다.
    - 영화 출연진 테이블에 출연진 정보를 생성한다.
    - 영화 장르 테이블에 장르 정보를 생성한다.

### 영화 수정하기

- 관리자 권한이 존재해야 한다.
- 입력
    - 수정할 영화 ID를 입력받는다.
    - 수정하고자 하는 영화제목, 시놉시스, 상영 시간, 영화 등급, 포스터, 개봉일, 배급사명, 감독 ID를 입력으로 받는다.
    - 수정하고자 하는 상영 유형 리스트를 입력으로 받는다.
    - 수정하고자 하는 배우 ID와 역할, 캐스팅 타입 리스트를 입력으로 받는다.
    - 수정하고자 하는 장르명 리스트를 입력으로 받는다.
- 검증
    - 0 < 상영시간(분) < 1000
        - 실패 시 `Bad Request` 예외를 발생시킨다.
    - 영화ID가 영화 테이블에 존재하는지 확인한다. soft-delete된 영화여서는 안된다.
        - 실패 시 `Not Found` 예외를 발생시킨다.
- 다음을 하나의 트랜잭션으로 수행한다.
    - 포스터가 변경되었다면, 새 포스터를 스토리지에 저장하고 기존 포스터를 제거한다.
    - 영화 테이블에 영화를 수정한다.
    - 영화 ID를 기반으로 상영 유형, 출연진 정보와 장르 정보를 가져온다.
        - 입력으로 받은 상영 유형 정보가 존재하지 않으면, 새로 추가한다.
        - 입력으로 받은 출연진 정보가 존재하지 않으면, 새로 추가한다.
        - 입력으로 받은 장르 정보가 존재하지 않으면, 새로 추가한다.
    - 입력으로 받은 상영 유형 정보, 출연진 정보와 장르 정보에 없는 조회 결과는 삭제한다.

상영 유형, 출연진, 장르 정보를 일괄 삭제하고 삽입하기 vs 존재하는지 확인하고 수정하기

### 영화 삭제하기

- 관리자 권한이 존재해야 한다.
- 입력
    - 삭제할 영화 ID를 입력받는다.
- 검증
    - 상영 일정이 존재하는지 확인한다.
        - 상영 일정 존재 시 `Bad request` 예외를 발생시킨다.
- 다음을 하나의 트랜잭션으로 수행한다.
    - 기존의 영화 상영 기록 등의 정보를 유지해야 하므로, 영화 테이블에서 영화를 soft-delete한다.

**→ 그냥 삭제? 더 검증해야 하는 요소는?**

### 영화 상세 조회하기

- 입력
    - 영화 ID를 입력받는다.
- 반환
    - 영화제목, 시놉시스, 상영 시간, 영화 등급, 포스터, 개봉일, 배급사명을 반환한다.
    - 감독ID, 감독명을 반환한다.
    - ~~상영 유형 리스트를 반환한다.~~
    - 배우ID, 배우명과 역할, 캐스팅 타입 리스트를 반환한다.
    - 장르명 리스트를 반환한다.

### 영화 간단 조회하기

- 입력
    - 영화 ID를 입력받는다.
- 반환
    - 영화제목, 포스터, 개봉일을 반환한다.

영화 홈, 감독 상세, 배우 상세 등에서 사용

### 영화 검색하기(영화 제목)

- 입력
    - 검색어를 입력받는다.
        - 영화 제목을 검색하며, 부분 검색이 가능하다.
    - 필터링 기준을 선택적으로 입력받는다. 개봉일, 장르, 상영 유형들을 입력받을 수 있다.
        - 기본 개봉일 필터링은 현재 날짜로부터 1달 전 ~ 7일 후이다.
    - 정렬 기준을 한 가지 선택하여 입력받는다. 개봉일순, 인기순 중 하나를 입력받는다.

## PRIORITY-CRITICAL

### 상영일정별 상영 좌석 현황 조회하기

- 예매 가능한 좌석이 존재하지 않거나 || 예매 가능 최대 시각 (시작 시간 30분 전)을 지난 경우 `Bad Request 400`를 반환한다.
- 상영 일정에 따른 상영 좌석들의 현황 (예매 가능, 예매 완료, 사용 불가, 규격)을 조회하여 반환한다.
    - 상영관 규격과 상영관의 모든 상영 좌석 리스트와 상영 일정의 예매 좌석 리스트가 모두 필요하다.
- *조회가 잦고, 많은 join이 필요하므로 매번 db에서 조회하기보다 캐시를 사용함이 적합하다*

### 예매하기

- 유효한 고객만이 예매 가능하다.
    - 유효한 고객: 탈퇴하지 않고, 존재하는 고객
- 필요한 데이터가 모두 유효한 값인지 확인한다: 상영일정 ID, 고객 유형별 예매 인원 수, 선택한 상영관 좌석 ID 리스트
    - 총 예매 인원 수는 0보다 크고 10보다 작아야한다.
- 총 예매 인원 수와 선택한 좌석 수가 일치해야한다.
- 선택한 좌석은 예매 진행중이거나 완료되지 않은 좌석이어야한다.
- 해당 상영 일정의 상영 시간으로부터 10분 전까지만 예매가 가능하다.
- 위 조건을 모두 만족시킨 유효한 티켓인 경우 예매 진행중 (PROGRESS) 상태로 전환된다. 결제 취소 혹은 예매 취소 이벤트가 발생하거나 해당 상태로 전환된 후 30분 이상이 지난 경우 예매 취소 (CANCELED) 상태로 전환된다.
- *상영일정별 상영 좌석 현황 캐시를 업데이트한다.*
    - *실패하는 경우 주기적으로 재시도한다. n번 이상 실패하는 경우 개발자에게 알림을 보낸다.*

### 결제하기

**step-1: 결제 요청**

- *유효한 고객인지는 확인하지 않는다. 예매하기와 연속적으로 수행되는 기능이고, 예매 시 유효 고객 검증이 진행되기 때문이다.*
- 결제하고자 하는 예매 내역은 유효해야한다
    - 상태가 `PROGRESS`여야한다.
- 금액 (총 가격, 할인가, 포인트, 결제 가격)을 검증하고, 올바른 값이 아닌 경우 예외를 발생시키고, 올바른 값을 반환한다.
    - 총 가격: 고객 유형별 { 예매 인원 수 * (예매하는 영화 유형에 따른 영화 가격 - 고객 유형별 할인가) } 총합
    - 할인가: 선택한 결제 수단의 제휴사에 따른 할인가
        - 총 가격보다 큰 경우 총 가격과 동일하게 변경한다.
    - 포인트: 사용할 포인트
        - 해당 회원이 보유한 포인트 ≥ 1000 && 보유 포인트 ≥ 사용하고자하는 포인트 && 사용하고자하는 포인트 ≥ 1000 인 경우에만 사용 가능, 이외에는 예외 발생
        - 할인가 + 포인트 ≤ 결제 가격까지만 포인트를 사용할 수 있다.
    - 결제 가격: 총 가격 - 할인가 - 포인트
        - 결제 가격은 0원 미만일 수 없다.
    - 적립될 포인트: 결제 가격 * 0.01
- 금액이 올바른 경우 결제 내역을 저장하고, 결제 id와 적립될 포인트를 반환한다.

**step-2: 결제 완료**

- 결제가 완료된 경우 결제 id와 함께 승인 번호를 받는다.
- 결제 내역을 업데이트한다.
- 유효한 예매 내역인지 확인한 후 유효한 예매 내역이 아닌 경우 환불 처리하고 예외를 반환한다.
- 유효한 예매 내역인 경우 해당 예매 내역의 상태를 `DONE`으로 업데이트한다.

**step-2: 결제 실패 (에러) / 취소 (사용자 의도)**

- 결제가 실패 혹은 취소되는 경우에는 서버에 어떠한 요청도 보내지 않는다.
- 새롭게 결제 요청을 보내면, 새로운 결제 내역이 생성된다.

고민한 사항

- 프론트에서 계산하여 총 가격 제시 or 매번 서버에 결제 가격 계산 API 전송
    - 이는 결국 프론트의 값을 신뢰도 있는 값으로 만들기 위함인데, 이 값은 쉽게 변경이 가능함 → 보안에 취약
    - 프론트에서는 임시 가격으로 계산하여 보여주기
    - 이것에 대한 정합성이 중요한 서비스 (호텔 / 비행기 등 예약-사용자 및 시간대에 따라 가격이 달라짐)의 경우 서버에 주기적으로 가격을 불러오는 api를 수행하여 값을 업데이트시키는 것으로 암
- 프론트에서 보낸 값 신뢰 or 서버에서 최종 계산
    - 따라서 서버에서 최종 계산함이 옳음

짧게 고민한 사항

- 결제는 요청한 후에 곧 해당 정보를 조회하게 된다. 그렇다면 캐시를 두는 것이 적절한가?
    - 빈번하게 조회되지 않는다. 즉, 낭비이다.
    - 또한 결제의 경우에는 정확한 상태가 필요하기 때문에 DB에서 직접 조회가 옳다.

## PRIORITY-HIGH

### 예매 취소하기

- 유효한 예매 상태여야한다: `PROGRESS`, `DONE`
- 고객이 `DONE`인 예매를 취소하는 경우, `PROGRESS`인 예매 내역이 생성된 지 30분이 지날 동안 업데이트되지 않은 경우, 배치 작업을 통해 수행된다. 그 외에는 `ForbiddenException`을 발생시킨다.
- 예매 상태를 `CANCELED`로 업데이트한다.
- 예매 취소 이벤트가 발생한다. 환불 및 포인트 반환 / 회수가 진행된다.

### 환불하기

**step-1: 환불 요청하기**

- **api로 요청이 불가하다. 예매 취소하기 시 자동으로 수행되거나, 올바르지 않은 결제가 수행된 경우에만 수행된다. (event)**
- 예매 내역의 완료된 결제 내역이 없는 경우 진행되지 않는다.
- 결제 내역에 대한 환불 내역이 존재하지 않는 경우 환불 내역이 생성된다. 환불 내역이 존재하는 경우 예외를 발생시킨다.
    - *~~double write이 발생하면 안된다. 오라클의 기본 트랜잭션 격리 수준인 READ COMMITED는 이를 보장하지 않기 때문에 SERIALIZABLE이 필요하다. 해당 수준은 트랜잭션 단위로 설정이 가능하기 때문에 결제에 대한 격리 수준만 따로 설정하면 될 듯하다~~*
    - PK가 결제 번호이므로 double write은 발생하지 않는다.
- 환불 내역을 생성한 경우 환불 요청이 완료된다.
- *비동기로 진행되며, 환불이 완료될 때까지 주기적으로 재수행한다. n회 재수행 시 개발자에게 알림 (`ERROR`)이 간다*

**step-2: 환불 외부 API 호출**

- *비동기로 진행된다. 실패 시 n회 반복된다*

**step-3: 환불 완료**

- 환불 승인 번호를 업데이트한다.

**step-3: 환불이 완료되지 않는 경우**

- 주시적으로 환불 내역의 환불 승인이 업데이트되었는지 확인한다.
- 환불 승인이 업데이트되지 않은 경우, 결제 번호를 통해 환불 처리가 되었는지 확인한다.
    - 환불 처리가 완료되었는데 환불 승인 요청이 전송되지 않은 경우, 환불 승인처리한다.
    - 환불 처리가 완료되지 않은경우, 서버에서 결제 정보를 갖고 환불 요청을 시도한다.
        - 환불 요청이 실패하는 경우 n회 재시도한다.

### 포인트 적립하기

- **api로 요청이 불가하다. 결제 완료 시 자동으로 수행된다. (event)**
- 결제한 금액의 1%를 포인트로 적립한다.

*유효한 고객인지 검증은 필요 없다. 예매 시점에서 이루어지기 때문이다.*

### 포인트 반환/회수하기

- **api로 요청이 불가하다. 환불 시 자동으로 수행된다. (event)**
- 해당 결제 내역에서 적립된 포인트는 회수하고, 사용한 포인트는 반환하여 포인트 내역에 각각 저장한다.

정리

- 포인트는 예매가 아니라 결제와 같이 수행된다.
- 포인트가 적립되는 시점은 결제가 완료되는 시점이며, 예매 취소 시에도 곧바로 환불 완료가 되지 않기 때문이다.
- 사용자는 예매와 예매 취소만 수행할 수 있으며, 그 안에서 결제와 포인트, 환불이 수행된다.

### 상영 일정 조회하기

- 날짜가 필수적으로 주어져야하며, 영화는 선택적으로 전달될 수 있다.
    - 날짜만 주어진 경우 영화별, 그 안에서 상영관별 상영 일정이 제시된다.
    - 날짜와 영화가 주어진 경우 상영관별 상영 일정이 제시된다.
    - 영화 등급 로고와 영화명, 상영 유형과 상영관, 상영관 총 좌석 수, 상영일정별 예매된 좌석 수를 조회하여 반환한다.
- *날짜별 상영 일정의 경우 데이터 변경이 적고 조회가 빈번하기 때문에 캐시를 사용한다.*
