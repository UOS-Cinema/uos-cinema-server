# 테이블 설계

## 장르는 어디에 저장할까?

장르는 어디에 저장하는 게 좋을까? DB Table vs ENUM vs Application

- DB table로 관리하는 경우 확장성과 정합성 측면에서 유리하다
    - 추가 및 삭제/변경 시의 데이터 정합성을 지키기 쉽다
    - 장르에 대한 기타 활용이 가능하다
        - 추가 설명 및 사진, 인기도 등
        - 추천 시스템 등에 활용
    - 장르에 대해서 매번 조인이 수행되어야하며, 장르 조회 또한 DB를 거쳐야만한다.
- ENUM으로 관리하는 경우 간편하나, 장르에 대한 변경사항이 생기는 경우 테이블이 변경되므로 확정성이 낮다.
- Application으로 관리하는 경우 DB와 완전히 분리 가능하다
    - 장르 수정 시 코드만 수정하고 재배포하면 된다
        - 장르 변경만 되어도 서버가 재배포 되어야한다
        - 코드는 변경사항을 추적/관리하기 용이하다
    - 데이터 정합성 보장이 어렵다
    - 확장성에 제한이 있다

Table을 선택한 이유

- 적은 수가 x: 20개 가량의 장르가 존재
- 미래에 새로운 장르가 나올 가능성
- 영화와 장르는 M:N 관계이므로
- 장르 조회 API의 경우 Application에서 캐싱하여 제공 가능 (매번 DB를 조회하지 않아도 됨)

## 고객 유형 / 상영 유형은 어디에 저장할까?

고객 유형은 예매에서 사용되며, 상영 유형은 영화 및 상영관에서 사용한다.

상영 유형은 정합성을 보장하기 위해서라도 테이블로 관리할 필요성이 존재한다.

왜냐하면 영화 및 상영관 정보와 직접적으로 연관되며, 정확한 상영 정보 제공이 중요하기 때문이다. 변경 가능성이 낮지만, 추가적인 속성(예: 추가 요금)이 붙을 수 있으므로 테이블로 관리하는 것이 적합하다.

반면 고객 유형은 도메인의 특성을 고려해야한다. 해당 시스템에서는 가격 정책을 설정할 수 있는데, 고객 유형은 가격 정책의 구성 요소 중 하나이다. 즉, 가격에 대해 관리하는 것이 DB에서 이루어진다면 고객 유형 또한 데이터베이스에 저장되어야한다.

## 예매에서 비회원 / 회원을 어떻게 지원할까?

예매의 경우에는 비회원과 회원 둘 다 가능하다.

그러면 예매 내역 - 결제 내역 - 환불 내역 등 예매와 관련된 테이블에서 어떻게 회원과 비회원 둘 다 지원할 수 있을까?

방법은 2가지이다.

1. 테이블마다 회원 / 비회원 속성 2개 존재
2. 비회원 / 회원을 동일하게 취급

### 테이블마다 회원 / 비회원 속성 분리(member_id, guest_id column)

상속 구조가 없어 불필요한 Join이 발생하지 않지만 언제나 Null이 존재하면 쿼리가 복잡해진다. 또한 새로운 회원 유형이 추가된다면 테이블이 변경되어야한다.

### 비회원 / 회원을 동일하게 취급 (Customers table)

모든 예매를 Customers 테이블에 연결하고, type column은 Member 혹은 Guest 중 하나로 구성된다. 회원/비회원 정보는 Members/Guests 테이블에 따로 저장된다.

이 경우 정규화된 테이블 형태로 확장성을 가지지만 정보를 가져오기 위해 Join이 필요하다.

### 결론: Cusotmer-Member, Guest Table

- **간결한 쿼리:** 회원/비회원 관계없이 customer_id를 통해 예매 내역 조회 가능.
- **확장성:** 향후 새로운 사용자 유형(예: 법인 회원) 추가 시에도 유연하게 대처 가능.
- **성능:** 예매의 customer_id컬럼 값을 사용하여 Member, Guest를 조회하는 쿼리 수는 적음. 반대로, Member 혹은 Guest에서 예매 내역을 조회하는 쿼리가 다수이기에 성능상 큰 문제가 발생하지 않음.

Member, Guest 테이블의 분리 이유?
Guest 테이블은 자주 삭제되고 포인트 적립 등의 권한이 다르기 때문에 분리하여 관리함이 유용하다.

## 결제/환불 내역 PK 설계

예매 내역당 하나의 결제 내역과 환불 내역을 갖게 된다. 그렇다면 결제 내역과 환불 내역의 PK는 예매 내역 ID로 설정하면 되는 걸까?

### 유저에게 보이는 내역은 1개이지만, 실제로는 내역이 더 존재할 수 있지 않을까?

가령, 은행을 통해 계좌이체로 결제를 요청했다고 해보자.

하지만 잔액이 부족하여 승인을 받지 못한 것이다.

그렇다면 승인 번호가 없는 결제 내역이 1개 남게 된다.

### 승인 되지 않은 결제 내역은 삭제하면 되지 않을까?

결제 요청은 비동기로 이루어진다. 즉, 언제 승인이 완료될지 모른다.

Timeout을 설정하고, 이후의 완료된 결제에 대해서는 자동 환불을 신청한다.

다만, 해당 Timeout까지 기다리는 것은 사용자에게 매우 불편한 상황일 것이다.

### 명시적으로 실패한 결제 내역은 삭제하면 되지 않을까?

가능하다.

하지만 네트워크 문제나, 결제사의 문제로 결제가 계속해서 지연된다면, 사용자 편의상 다른 수단으로 결제를 시도할 수 있어야한다.

따라서 하나의 예매 내역에 대해 여러 결제 내역이 필요하게 되고, 결제 내역은 자신의 ID를 따로 갖게 된다.

이는 환불 내역에 대해서도 동일하게 적용된다.

## 데이터 삭제 전략: Soft Delete & Hard Delete

### Soft delete인 경우

Soft Delete는 단순히 `deleted_at`에 타임스탬프를 넣는 거니까, 기본적으로는 **단일 `UPDATE` 쿼리**로 충분하다

```sql
UPDATE table SET deleted_at = NOW() WHERE id = ?;
```

하지만 실무에서든 다음과 같은 이유로 **Soft Delete 시 조회 → 예외처리 → 업데이트** 순서를 택한다:

**존재하지 않는 ID에 대한 요청을 구분하기 위해**

- 조회 없이 `UPDATE table SET deleted_at = NOW() WHERE id = ?` 해도
    
    → 영향받은 row 수가 0이면 알 수 있음
    
    → 하지만 이건 SQL 레벨에서만 확인 가능
    
- 존재하지 않는 ID에 대한 요청의 예외 처리를 하고 싶다면 명시적인 조회가 필요하다

**Soft Delete는 종종 상태 유효성 검증이 함께 필요**

- 삭제된 데이터가 조회되지 않도록 쿼리에 WHERE is_deleted = false 조건을 항상 추가해야 한다

**비즈니스 로직에서 Audit 또는 Event 발생이 필요한 경우**

- 삭제 직전에 특정 로직 실행 (ex. 로그 기록, 다른 시스템에 이벤트 발행)
- 삭제 요청자의 권한 확인

→ **도메인 객체를 조회해야만 판단 가능한 로직**이 있는 경우, 조회는 필수

⇒ **Member, 예매 내역, 결제 내역 등 중요 데이터 및 중요 데이터와 관계가 있는 데이터**는 Soft Delete를 적용하여 데이터 유실 방지 및 이력 관리를 용이하게 한다 (예: 회원이 탈퇴해도 예매/결제 이력은 남아있을 수 있음)

### Hard Delete

데이터를 데이터베이스에서 영구적으로 제거.

→ 디스크 공간 절약, 쿼리 성능 향상

→ 데이터 복구 불가능, 과거 이력 추적 어려움, 잠재적인 데이터 무결성 문제 발생 가능

**⇒ 캐시 데이터, 임시 로그, Guest 등 중요도가 낮은 데이터**는 Hard Delete를 적용하여 성능 및 저장 공간을 최적화할 수 있다

## 예매내역은 snapshot을 저장해야한다

### Issue 1: 상영관 좌석 hard delete 시 과거 예매 내역 null 출력

기존 기능 요구사항을 보면, 상영관 layout을 수정하는 경우 상영관 좌석을 hard delete 후 새로운 좌석을 생성한다.

헌데 이 경우, 해당 좌석을 FK로 갖고 있는 예매 내역이 null로 출력되는 상황이 발생하게 된다.

이것은 상영관에도 동일하게 적용된다.

그렇다고 soft delete를 하자니, 이 경우 유니크 제약이 충돌되는 경우가 생긴다. 이전 상영관의 이름이나 기존 상영관 좌석의 좌석번호 사용이 불가하기 때문이다.

이를 해결하기 위해서는 복잡한 복구 로직이 필요하다

- 생성 시 존재하는지 확인
    - 존재하면 deletedAt 제거 + 모든 값 초기화
    - 존재하지 않는 경우 생성

→ Soft delete는 데이터 복구가 필요하거나, 기록을 보존해야하는 경우에만 사용한다

⇒ 지금처럼 그다지 중요하지 않고 재사용성 확보가 필요할때는 불필요하게 복잡해진다

### Issue 2: 예매 ‘내역’은 ‘당시’의 상황을 표현해야함

또한 예매 내역은 ‘기록’을 뜻하기 때문에, ‘당시’의 상황을 나타내야한다고 생각한다.

즉, 예매 내역은 과거 상태를 재현할 수 있어야 하므로 절대 변형되지 않아야 한다.

가령, 상영관의 이름이 1관에서 Theater#1과 같은 형식으로 바뀐다고 했을 때, 이전 1관에서 예매한 내역은 그대로 ‘1관’으로 표시됨이 옳다.

### 1. `예매 내역`에 `고객 유형별 인원 수`와 `예매 좌석` snapshot 저장

FK로 남겨두면 참조 대상이 삭제되거나 변경되었을 때 무결성이 깨짐 → 과거 상태를 신뢰할 수 없음

⇒ String이나 Value Object 형태로 저장

### 2. 기존 관계 테이블 그대로 유지, hard delete 시 FK null

비즈니스 로직 처리에 관계 테이블이 필요한 경우가 있다.

가령 예매 좌석을 확인할 때에는, 해당 예매 좌석을 FK로 갖고 있는 예매 내역을 확인하게 된다.

이 관련 값이 삭제된 경우에는 null로 저장되게 한다.

oralce에서는 다음과 같이 설정할 수 있다.

```sql
ALTER TABLE reservation_seats
ADD CONSTRAINT fk_theater
FOREIGN KEY (theater_id)
REFERENCES theaters(number)
ON DELETE SET NULL;
```

다만 여기서 고객 유형별 인원 수는 비즈니스 처리에 필요한 경우가 존재하지 않기 때문에, `CASCADE DELETE`로 설정함이 옳다

### 확장

예매 내역 / 결제 내역 / 환불 내역 / 포인트내역은 그 당시의 snapshot을 저장
FK (movie, theater, customer)가 변경/삭제되어도 이전의 값을 그대로 유지

→ snapshot 컬럼 추가:
seat_snapshot, customer_count_snapshot, payment_method_snapshot 등
→ ON DELETE SET NULL 설정

# 개발

## Reference Data: 상수와 같은 값들을 매번 조회하는 게 과연 필요할까?

장르, 상영 유형, 카드사, 은행, 고객 유형 등의 값들은 수정이 거의 이루어지지 않으며, 조회가 빈번하게 일어난다.

이런 값을 매번 조회하는 것은 비효율적이다.

캐시를 사용하여 빠르게 읽어오면 어떨까?

캐시는 읽기 성능을 개선하기 위한 목적이다.

하지만 여기서의 목적은 ‘읽기 성능’보다 ‘비효율 개선’이 목적이다.

거의 변하지 않는 값이기 때문에 웹 어플리케이션 서버가 처음에 로드될 때 DB에서 값을 조회하여 계속 메모리상에서 직접 갖고 있는 방식을 사용함으로써 불필요한 DB/캐시 접근을 줄였다.

변경사항이 일어난 경우, 이를 감지하여 새롭게 로드해오도록 구현함으로써 데이터 정합성 또한 보장하였다.

## Registry 구현하기

**불변에 가까운 코드상 상수처럼 동작하는 데이터**를 런타임에 초기화해서 **애플리케이션 컨텍스트 안에 둔다.**

이로써 서버가 시작될 때, 특정 참조 데이터를 **메모리에 로딩해서 상시 보관**하고, DB에 대한 접근을 줄인다.

**요구사항**

| 항목 | 설명 |
| --- | --- |
| 데이터 | 상영유형, 장르, 고객유형, 은행, 카드사 (사실상 Lookup/Reference Table) |
| 특징 | 변경 거의 없음, 고정 값, 예외적 경우에만 Admin에서 변경 |
| 목표 | 서버 구동 시 1회만 로딩, 이후에는 애플리케이션 내부에서만 사용 (DB 접근 X) |
| 비선호 방식 | 매 요청마다 캐시 조회, TTL 기반 갱신 등은 원하지 않음 |

### 아키텍처: **불변 Lookup Map + 초기 로딩 + 의존성 주입**

### 1. 서버 시작 시 1회 로딩 (예: `@PostConstruct`, `@EventListener`)

```java
@Component
public class ScreenTypeRegistry {

    private final Map<String, ScreenType> screenTypeMap = new HashMap<>();

    @PostConstruct
    public void init() {
        List<ScreenTypeEntity> entities = repository.findAll();  // DB 접근 1회
        for (ScreenTypeEntity e : entities) {
            screenTypeMap.put(e.getType(), new ScreenType(e.getType(), e.getPrice()));
        }
    }

    public ScreenType get(String type) {
        return screenTypeMap.get(type);
    }

    public Collection<ScreenType> getAll() {
        return screenTypeMap.values();
    }
}

```

### 2. 필요한 서비스/도메인에서 주입해서 사용

```java
@RequiredArgsConstructor
@Service
public class TicketService {

    private final ScreenTypeRegistry screenTypeRegistry;

    public Money calculatePrice(String screenTypeCode) {
        ScreenType screenType = screenTypeRegistry.get(screenTypeCode);
        return screenType.getPrice();
    }
}

```

### 이로 인해 얻는 장점

| 항목 | 설명 |
| --- | --- |
| DB 접근 | 서버 구동 시 딱 1번 |
| 속도 | JVM 힙 내 참조 → 초고속 |
| 정합성 | 서버 살아있는 동안엔 고정 |
| 테스트 용이성 | Map만 Mocking 가능 |
| 타입 안정성 | VO 변환해서 도메인 계층에 전달 가능 |

```java
@Scheduled(fixedDelay = 6 * 60 * 60 * 1000) // 6시간마다 갱신

```

DB에서 전체 조회? 부분 수정?

| 방식 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| **① 전체 Reload** | 해당 도메인 전체를 DB에서 다시 조회하여 Map 교체 | 간단, 동기화 확실, 버그 적음 | 불필요한 I/O, 데이터 커지면 비효율 |

### DBInitializer
이때 테스트 격리를 위해 DBInitailaizer라는 클래스에서 table truncate, data setting을 수행한다.
DB에 쿼리를 수행하는 것은 크게 Datasource, entitymanager, jdbctemplate 을 사용할 수 있는데, DDL과 같은 것은 바로 수행되어야하므로 Datasource를 사용함이 좋다.
Test container의 경우 연결 후 기존의 registry 값을 덮어쓰는 등, 추가적인 작업이 많이 이루어진다. 따라서 정의한 Datasource를 그대로 사용하지 않고, 이 값이 정확히 언제 들어오는지 명시되어있지 않기 때문에 sprign di에 의해 주입됨이 옳다 -> @TestComponent'로 정의하여 @Autowired`로 주입받는다.

번외)
java code로 수행하는 게 아니라 truncate.sql, init.sql을 매번 수행하는 annotation을 구현할 수도 있지만, 수행하는 기능이 더 추가되었을 때를 고려하거나, 매 테스트 메서드 후에 수행되어야하므로 한 번 정의하는 것이 깔끔한데 어노테이션 사용 시 매 사용할 때마다 정의해야하는 번거로움 때문에 클래스로 구현했다.

### DBInitializeStrategy
이때 테스트 격리를 위해 DBInitailaizer라는 클래스에서 table truncate, data setting을 수행하는데, oracle과 h2 등의 사용 db에 따라서 수행되는 쿼리가 다르므로 해당 쿼리를 수행하는 DBInitializeStrategy interface를 생성하고, 이에 대한 OracleDBInitializeStrategy class를 구현했다.
